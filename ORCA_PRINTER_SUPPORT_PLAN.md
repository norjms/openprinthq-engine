# Plan: OrcaSlicer-wide printer support

Status: **PLAN — scope locked, ready to build.** Branch: `feature/klipper-extended`.

### Locked decisions
- **Build order:** framework generalization + Chunk 0 (import Klipper profiles) → Chunk 1 OctoPrint/PrusaLink → Chunk 2 Duet → Chunk 3 FlashForge → Chunk 4 MKS/other LAN → (Chunk 5 cloud, only if revisited).
- **Scope:** **FDM + LAN only.** Resin/MSLA **out**. Cloud relays **out** (revisit later).
- **Depth:** **full monitor + control + print** for each mechanism (not phased).
- **Profiles:** **curate popular models first**, expand over time (importer supports both; we gate the emitted set).
- **Deploy:** to `printer.nnlink.org` (dev clone) until proven; `bambu.nnlink.org` untouched.

Goal: support the printers in [OrcaSlicer `resources/profiles`](https://github.com/OrcaSlicer/OrcaSlicer/tree/main/resources/profiles) — geometry/capabilities from the profiles, control mechanisms from OrcaSlicer's print-host code (`src/slic3r/Utils/`).

## The one insight that makes this tractable: two orthogonal axes

A printer is "supported" only when **both** are true:

- **Axis 1 — Control client** (the engineering): a `PrinterClient` implementation for its *control mechanism* (protocol). There are ~a dozen mechanisms but they collapse into **~5 client families**. This is bounded work.
- **Axis 2 — Printer profile** (the data): geometry + capabilities (bed size, kinematics, extruder count, chamber). This is where the ~1000 machine files live — but it's **generated by an importer**, not hand-written.

We already did exactly this shape for Klipper (a Moonraker `PrinterClient` + a profile registry). This task = generalize that framework and add the other mechanisms.

## What OrcaSlicer actually gives us

**Control mechanisms** — the authoritative list is OrcaSlicer's `PrintHost` factory (`src/slic3r/Utils/PrintHost.cpp`), which maps `host_type` → implementation:

`htOctoPrint, htDuet, htFlashAir, htAstroBox, htRepetier, htPrusaLink, htPrusaConnect, htMKS, htESP3D, htCrealityPrint, htObico, htFlashforge, htSimplyPrint, htElegooLink, ht3DPrinterOS, htMoonraker` (+ `SL1Host` for resin, + `BBLPrinterAgent` for Bambu).

Each has a class in `src/slic3r/Utils/` (`OctoPrint.cpp`, `Duet.cpp`, `Moonraker.cpp`, `Flashforge.cpp`, `MKS.cpp`, `Repetier.cpp`, `Obico.cpp`, `PrintHost.cpp`, `CrealityPrint.cpp`, `QidiPrinterAgent.cpp`, …) — **this is the reference code for each mechanism's API + capabilities.**

**Scale of the profile list** — ~65 vendors; machine-file counts sampled: Creality 143, Prusa 77, Voron 74, Flashforge 61, Qidi 51, Anycubic 49, Sovol 36 … (many are nozzle-diameter variants of the same physical printer → a few hundred *distinct* models). Note several vendors are **resin** (Phrozen, Peopoly, parts of Elegoo/Anycubic) — a different control domain (SDCP/ChiTu), flagged as out-of-scope below.

**Bambuddy already covers 2 mechanisms:** Bambu Lab (MQTT/TLS+FTP) and Moonraker/Klipper (WebSocket JSON-RPC).

## Control-mechanism groups (the chunks)

Ordered by coverage-per-effort. Each is a distinct `connection_type` + `PrinterClient` implementation, reusing the existing abstraction (`printer_client.py`, `printer_capabilities.py`, profile registry, WS status → shared `PrinterState`, frontend add-dialog + card gating).

### Chunk 0 — Klipper-based printers via the EXISTING Moonraker client *(quick, huge win)*
- **Mechanism:** `htMoonraker` (and effectively `htCrealityPrint`, `htQidi`/`QidiPrinterAgent`, much of `htElegooLink`, `htObico`-LAN — these are Klipper printers whose vendor "agents" wrap Moonraker).
- **Printers:** most modern consumer Klipper machines — all Vorons (done), RatRig, Vzbot, SecKit, Sovol SV0x-Klipper, **Creality K1/K2/Ender-3 V3 (Klipper)**, **Qidi Plus4/X-Max3/X-Plus3**, **Elegoo Centauri (FDM)**, **FlashForge AD5M**, BIQU, FLSun (Klipper). Many are reachable at Moonraker `:7125` directly (developer/root mode) or via the vendor's Moonraker port.
- **Work:** no new client — just **import their profiles** (Axis 2) + per-vendor connection quirks (port, optional API key, camera path). Chamber/kinematics auto-discovered as we already do.
- **Effort: LOW. Coverage: the single biggest block of modern printers.**

### Chunk 1 — OctoPrint REST family
- **Mechanisms:** `htOctoPrint`, `htPrusaLink`, `htAstroBox`, `htESP3D`, `htRepetier`.
- **Protocol:** HTTP REST + `X-Api-Key`. Upload g-code (`/api/files/local`), control via `/api/job` + `/api/printer/command`, live status via `/api/printer` polling **or** the SockJS push socket. PrusaLink adds `/api/v1/status` and is OctoPrint-legacy-compatible.
- **Printers:** the entire **Prusa** fleet (MK4/MK3.9/MINI/XL via PrusaLink), plus **any Marlin/RRF printer running OctoPrint** (huge long tail: Creality Ender classic, Anycubic, Artillery, Elegoo Neptune, Sovol, etc.).
- **Work:** one solid `OctoPrintClient` + a thin `PrusaLinkClient` subclass. Repetier/AstroBox/ESP3D are OctoPrint-shaped variants (later).
- **Effort: MEDIUM. Coverage: Prusa + all OctoPrint users — second-biggest block.**

### Chunk 2 — Duet / RepRapFirmware
- **Mechanism:** `htDuet`.
- **Protocol:** Duet Web Control HTTP API — `rr_connect`, `rr_upload`, `rr_gcode`, and the **object model** (`rr_model`/`rr_status`) for rich status.
- **Printers:** Duet-board machines — RatRig V-core, E3D toolchanger, some Vorons, high-end custom CoreXY.
- **Effort: MEDIUM. Coverage: the high-end/maker segment.**

### Chunk 3 — FlashForge LAN protocol (proprietary TCP)
- **Mechanism:** `htFlashforge`.
- **Protocol:** TCP socket on **:8899**, M-code framing (`~M601` login, `~M105` temps, `~M27` progress, `~M28/M29` upload, `~M23` print). Status is poll-only (limited).
- **Printers:** older/mid FlashForge (Adventurer 3/4, Creator, Guider). (AD5M/newer are Klipper → Chunk 0.)
- **Effort: MEDIUM-HIGH (bespoke TCP + M-code). Coverage: FlashForge fleet.**

### Chunk 4 — Other vendor LAN protocols
- **Mechanisms:** `htMKS` (MKS WiFi module — TCP M-code), residual `htElegooLink` (SDCP for some Elegoo), `htCrealityPrint` non-Moonraker path.
- **Effort: MEDIUM per protocol. Coverage: the remaining LAN-controllable Marlin printers.**

### Chunk 5 — Cloud relays *(optional / later)*
- **Mechanisms:** `htObico` (cloud), `htSimplyPrint`, `ht3DPrinterOS`, `htPrusaConnect`, Bambu cloud.
- Require accounts/OAuth; overlap with the LAN methods. Value = remote-without-VPN. **Deprioritize** for a self-hosted LAN tool unless explicitly wanted. (We already integrate Obico for AI detection — the relay could be reused.)

### Out of scope (initially)
- **Resin/MSLA** printers (SDCP/ChiTu — Elegoo Saturn/Mars, Phrozen, Anycubic Photon, Peopoly): different control + workflow domain. Flag separately.
- `htFlashAir` (SD-card WiFi, deprecated), `SL1Host`.

## Axis 2 — the profile importer (data pipeline)

A build/CI script that converts OrcaSlicer machine JSONs → Bambuddy printer profiles:
- Parse each `resources/profiles/<Vendor>/machine/*.json`: `printable_area` → bed size, `printable_height`, `nozzle_diameter`/extruder count, `printer_structure`/`gcode_flavor` → kinematics (bed-slinger vs CoreXY vs delta), name → model.
- Dedupe nozzle-diameter variants into one model.
- Emit a generated `printer_profiles` dataset (extends today's hand-written `klipper/profiles.py` into a generic, generated registry keyed by vendor+model).
- Attach a **default control mechanism** per model (heuristic from firmware/vendor: Bambu→bambu, Voron/Ratrig/K1/Qidi→moonraker, Prusa→prusalink, Duet-boards→duet, FlashForge-classic→flashforge, else→octoprint) — user-overridable, exactly like OrcaSlicer's `host_type` picker.

Keeping this generated means "add 200 more printers" is a data refresh, not code.

## Framework generalization (prerequisite, small)
Today's code is Klipper-named in spots. Before Chunk 1 we lift it to a generic "external printer" framework:
- `connection_type` becomes an open enum (`bambu, moonraker, octoprint, prusalink, duet, flashforge, mks, …`).
- `services/klipper/` stays; add sibling packages `services/octoprint/`, `services/duet/`, etc., each with a `PrinterClient`.
- `printer_capabilities.py` generalizes (per-mechanism capability sets).
- Frontend add-dialog: connection-type list grows; model dropdown filters to mechanisms that fit, and selecting a model suggests its default mechanism.

## Recommended sequencing
0. **Framework generalization** + **Chunk 0** (import Klipper-based profiles) — immediate broad coverage on the client we already have.
1. **Chunk 1** OctoPrint + PrusaLink — Prusa + OctoPrint long tail.
2. **Chunk 2** Duet.
3. **Chunk 3** FlashForge, then **Chunk 4** MKS/others.
4. **Chunk 5** cloud relays (if wanted).
Profile importer lands with step 0 and is re-run as each mechanism's printers come online.
